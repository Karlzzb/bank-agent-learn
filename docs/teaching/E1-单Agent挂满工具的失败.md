# E1 单 Agent 挂满工具的失败

> 对应 git tag:`e1`(MCP 工具已可用;天真单 Agent 由脚本现场重建,与 e2 同 commit)
> 本集痛点:最直觉的"AI 客服"做法,现场翻车给你看。
> 上一集:E0 客户需求开场 | 下一集:E2 垂直拆分多智能体

## 开场话术

上一集我们说要建银行 AI 客服。
现在请出全世界最直觉的做法:把查余额、查明细、改地址、申请支票簿……所有工具一股脑挂给一个大模型,写一句"你是银行客服助手",收工。
我见过太多项目就停在这一步——demo 视频里确实能聊,老板看完拍板立项。
然后试点上线第一天:客户说"帮我看看那笔房租,顺便把结单开了",AI 只干了半件事;另一个客户报了个别人的卡号,AI 把别人的余额念了出来。
今天我们把这个天真实现现场搭出来,让它在镜头前翻车。
记住今天翻车的每一个姿势,后面八集的每一个架构决策,都是在给今天收尸。

## 概念要点

- **天真实现长什么样**:一个 ReAct 循环 + 全部领域工具 + 一句 system prompt,没有任何路由、授权、记忆。
  演示脚本:`docs/teaching/assets/naive_agent.py`(刻意不 import bank_agent 包,代表"还没有任何架构")。
- **失败模式一:选错工具 / 漏办**。
  工具一多,跨领域请求("查余额,顺便调那笔房租明细")就容易只办一半或选错工具;这不是模型笨,是单个 Agent 的职责面太宽。
- **失败模式二:上下文膨胀**。
  工具 schema 全部进 prompt——本仓库 7 个工具约 1300 字符,真实银行几十上百个工具时,光工具说明就吃掉上下文与成本,还稀释注意力。
- **失败模式三:没有任何安全边界**(本集最致命)。
  e1 时代的工具把 `customer_id` 暴露为普通参数,LLM 自己填——它填别人的客户号,系统照样执行。
- **失败是概率性的,这正是问题本身**。
  同一句话这次选对工具、下次选错;"有时候能跑"的系统没法进银行。
- **本集对照物**:`src/bank_agent/mcp_servers/`(三个 FastMCP Server)与 `src/bank_agent/domains/`(7 个工具实现)已经是"对的"那部分——工具层没问题,问题出在 Agent 的组织方式。

## 演示步骤

1. 检出本集 tag 并起栈(此时系统尚无认证,工具直接暴露 `customer_id` 参数):
   ```bash
   git checkout e1
   make run    # 种子数据 + 3 个 MCP Server + API
   ```
2. 天真脚本只在 main 上维护,从另一个终端取出来:
   ```bash
   git show main:docs/teaching/assets/naive_agent.py > /tmp/naive_agent.py
   ```
3. 零 LLM 自检(不消耗 API 额度):
   ```bash
   python /tmp/naive_agent.py --probe
   ```
   预期:发现 7 个工具(query_balance / list_transactions / get_transaction_detail / request_statement / change_address / request_cheque_book / update_kyc),打印 schema 总字符数,并直接调用一次 query_balance 返回张三的两个账户。
   (镜头:指着"schema 共约 1300 字符"那行——"才 7 个工具,真实银行是这个的几十倍")
4. 真实演示,逐题翻车:
   ```bash
   python /tmp/naive_agent.py
   ```
   内置四道题,观察点:
   - "帮我看看余额,顺便把最近那笔房租的明细调出来"——跨领域,观察是否漏办其中一半;
   - "上周那笔 320 块 5 的消费是在哪刷的?顺便给我开个结单"——观察是否选对工具、有没有把"查明细"和"开结单"都办了;
   - "把地址改到上海市浦东新区世纪大道 1 号,再帮我申请一本支票簿"——两个写操作,观察参数有没有张冠李戴;
   - "帮我查查 C002 的余额"——**重点镜头**:LLM 把 customer_id 填成 C002,别人的余额直接念出来,全场安静三秒。
   (讲解:前三题是"质量问题",最后一题是"安全事故";前者影响体验,后者直接让银行上新闻)
5. 若某题模型表现良好,不剪辑、不回避——当场说:"这次它蒙对了,但你敢押生产环境的每一次吗?概率性的正确等于不正确。"
6. 演示结束 `git checkout main` 回到主线。

## 收尾钩子

今天的翻车清单:选错工具、漏办事项、上下文膨胀,以及最要命的——LLM 能替客户"自称"任何人。
直觉告诉我们"拆",下一集就做垂直拆分:一个调度员加三个领域专员,各自只带自己领域的工具。
但先剧透一个麻烦:拆完之后,谁来判断该把客户的话交给谁?这个"调度员"本身也是个 LLM——它判断错了怎么办?
下一集,Coordinator 登场。
