# E6 PII 脱敏:不把客户的手机号发给第三方大模型

> 对应 git tag:`e6`(PII 代码实际在 e3 的 commit 已并入,e6 tag 单调包含,见 README 对照表)
> 本集痛点:客户随口报出的手机号、身份证号、卡号,每一句话都原样落在第三方大模型的服务器上。
> 上一集:E5 记忆管理 | 下一集:E7 可观测性与成本

## 开场话术

先想一个最日常的画面。
客户打电话进客服中心,开口就是:"我手机号是 138 开头那个,身份证号我报给你,你帮我查查那张卡。"
这在银行业务里天经地义,不报身份信息反而办不了事。
所以你不能靠"让客户别说"来解决这个问题,客户一定会说,而且说得越多越好办业务。
但我们的客服不是人,是一个第三方大模型 API。
也就是说,客户报出来的每一个手机号、每一个身份证号、每一个卡号,都会原封不动地变成一次 HTTP 请求,落在别人公司的服务器上,留在别人的日志里,甚至可能进入别人的训练语料。
你没有删除键,那些数据一旦发出去,就不归你管了。
有一天合规部门来问一句话:"上线三个月,哪些客户的哪些数据出境了?"
这个问题看似简单,其实要命:它问的不是"你有没有加密",而是"数据到底去了哪"。
如果系统答不上来,这不是技术债,这是事故,是能上监管通报的那种。
有人第一反应是"那我们在合同里加条款、选国内部署的模型"。
这些是采购手段,不是工程手段,模型供应商的日志策略、子处理方列表、数据驻留承诺,你一样都验证不了。
工程上唯一能验证的承诺只有一条:发出去的请求里,压根没有真实数据。
更憋屈的是,很多时候大模型根本不需要知道真实号码。
它只需要知道"这里有一个手机号,和上一句提到的是同一个",就能把意图理解对、把工具调对。
占位符对它就是完美的"这里有一个手机号"——有类型、有编号、指代稳定,除了不是真号码,什么都是。
真实的号码,只有最终执行工具的银行系统自己需要。
这给我们一个关键洞察:可以把"理解意图"和"接触真值"分开。
大模型负责理解意图,只碰占位符;银行系统负责执行,拿到真值;两边各司其职,中间那道边界由我们自己的代码把守。
今天我们给系统加三道闸门:进门脱敏、工具层还原、出门回填。
目标是让大模型从头到尾只见过占位符,而客户完全无感。
顺便交代一句代码沿革:这套 PII 代码其实在第三集认证授权那个 commit 就一并落库了,本集只是第一次专门讲它,e6 tag 包含它的完整形态,大家用 tag 对照即可。

## 概念要点

- **为什么是确定性规则,而不是 NER 或 Presidio**:银行场景的 PII 格式高度规则化,身份证号 18 位、卡号 16 到 19 位、手机号 1 开头 11 位,正则就够了(`src/bank_agent/pii.py` 的 `_PATTERNS`)。
  注意口径分工:NER/Presidio 这类方案的权衡只在教案里讨论,代码里不出现、不依赖,演示步骤第 6 步有完整讲法。
- **三条规则按长度降序匹配**:身份证规则排在卡号规则前面,否则一个 18 位的证件号会先被 16 到 19 位的卡号规则截走(`src/bank_agent/pii.py` 的 `_PATTERNS` 顺序)。
- **误伤控制同样重要**:金额、笔数、月份这些普通数字不能脱敏,否则业务数字全变成占位符,大模型连"余额多少"都答不了(`tests/test_pii.py` 的 `test_amounts_and_short_numbers_not_masked`)。
- **姓名用静态映射表**:mock 阶段硬编码"张三""李四",接真系统时从客户主数据加载(`src/bank_agent/pii.py` 的 `KNOWN_NAMES`)。
- **占位符映射表是会话级状态**:形如 `{"[PHONE_1]": "13800001111"}`,存在会话 state 的 `pii_map` 里,随 checkpointer 持久化,续聊时编号继续稳定(`src/bank_agent/chat.py` 的 `invoke_chat`)。
- **映射表绝不能进大模型的 prompt**:它只走 config 通道和会话 state,和 E3 里 token 的待遇一样——凭证与真值,大模型都碰不到(`src/bank_agent/chat.py` 的 config 拼装)。
- **同一真实值复用同一占位符**:大模型看到的指代前后一致,才能正确理解"还是刚才那个号码"(`src/bank_agent/pii.py` 的 `_placeholder_for`)。
- **三道边界各管一段**:入站由 `chat.py` 在消息进图前脱敏;工具层由 `tool_providers.py` 的 `_rehydrate_args` 还原入参、`_mask_result` 脱敏结果;出站由 `chat.py` 用 `rehydrate` 回填最终回复。
- **长期记忆不许带走 PII**:记忆提取结果里凡含占位符的条目一律丢弃,store 不落任何 PII(`src/bank_agent/memory/nodes.py` 的 `contains_placeholder` 过滤)。
- **为什么占位符必须丢弃而不是回填**:占位符是会话作用域的标记,跨会话的 store 里即使回填也可能拿错映射,最安全的策略就是不让它出会话(`src/bank_agent/pii.py` 的 `PLACEHOLDER_PATTERN` 注释)。

## 演示步骤

1. 检出本集 tag:
   ```bash
   git checkout e6
   ```
   预期:工作区切到 e6 快照,`src/bank_agent/pii.py` 与 `tests/test_pii.py` 均在位。
   口头交代一句:PII 的代码其实在第三集那个 commit 就并进来了,按我们"看完第 N 集应具备全部能力"的单调包含原则,本集用 e6 tag,代码完全一样。
   这集的演示方式也和前几集一样:起栈、开 CLI、真对话,外加一个证据环节——单元测试。
2. 起栈,另开一个终端进 CLI:
   ```bash
   make run
   # 另一个终端:
   make cli
   ```
   预期:种子数据就绪、三个 MCP Server 与 API 启动;CLI 打印"银行客服已就绪(客户 C001)"。
   注意 e6 这个 tag 还没有接入 Langfuse,本集看不到 trace,那是下一集的事;本集的证据全部来自行为观察和单元测试。
3. 在 CLI 里输入一句含真实手机号的话:
   ```text
   我的手机号是 13800001111,帮我查一下余额
   ```
   预期:客服正常回复余额,而且回复里出现的是真实手机号 13800001111,客户完全无感。
   这里请先压住一个直觉反应:回复里出现真实号码,恰恰说明系统工作正常。
   客户是数据的主人,他当然有权在自己的屏幕上看到自己的号码;要防的是号码流向第三方大模型,不是流向客户自己。
   (镜头重点:这就是出站回填。
   此刻大模型看到的输入是"我的手机号是 [PHONE_1]",它产出的回复里写的也是 [PHONE_1],是系统在出口处按映射表换回了真实值。)
   再补一句讲解:查余额这个工具根本不用手机号做入参,所以这一轮里真实号码全程闲置——它存在的唯一意义是"客户说过",而大模型只需要知道"客户说过一个号码"。
4. 再追问一句复用同一号码的话:
   ```text
   就用刚才那个手机号,帮我查查最近的流水
   ```
   预期:回复正常,且指代理解正确。
   (讲解:同一个真实值在同一会话里永远映射到同一个 [PHONE_1],大模型看到的指代是一致的,所以"刚才那个"它接得住。)
   这里可以补一刀:如果观众问"那大模型会不会自己编一个手机号出来",答案是它编也没用,工具入参在工具层还原时只认映射表里存在的占位符,编出来的号码根本对不上任何真实客户。
5. 打开测试文件,逐条讲断言,这是本集的证据环节:
   ```bash
   # 在编辑器里打开 tests/test_pii.py
   ```
   开场先点题:这个文件没有任何网络调用、没有任何模型参与,全是字符串进、字符串出,这才是安全组件该有的测试形态。
   预期看到的断言与讲解词:
   - `test_mask_phone_id_card_and_card`:一句话里三类 PII 同时被替换成 [PHONE_1]、[ID_CARD_1]、[CARD_1],映射表内容精确匹配;
   - `test_id_card_takes_priority_over_card_pattern`:18 位证件号不会被卡号规则截获,这是规则顺序存在的理由;
   - `test_same_value_reuses_placeholder` 与 `test_numbering_continues_across_calls`:同一号码跨轮次复用同一占位符,新号码编号递增;
   - `test_amounts_and_short_numbers_not_masked`:金额、笔数、月份这类普通数字不误伤,映射表保持为空;
   - `test_rehydrate_restores_real_values` 与 `test_rehydrate_keeps_unknown_placeholder`:回填还原真实值,未映射的占位符原样保留,不臆造;
   - `test_mask_does_not_remask_placeholders`:脱敏是幂等的,占位符本身不会被二次命中,这一性质保证了"结果再过一遍脱敏"的链路安全。
6. 讲解为什么不引入 NER 或 Presidio(纯口播,不切代码):
   第一,为了识别敏感信息而引入另一个模型,本身就是新的不确定性和新的依赖;
   第二,NER 的误识别就是漏脱敏,漏脱敏就是泄露,而确定性规则可以单测、可以审计、推理成本为零;
   第三,真遇到非规则化的 PII 场景再评估 NER,那时它是增量,不是替代。
   一句话收口:在安全边界上,无聊的技术就是好技术,正则表达式无聊得刚刚好。
7. 跑一遍测试收个尾(零 API 消耗):
   ```bash
   make test
   ```
   预期:全部通过,其中 `tests/test_pii.py` 的用例逐一变绿。
   强调一句:确定性规则最大的红利就在这里——每一条脱敏行为都有对应断言,合规来审计时,你交出去的是一份测试报告,不是一份承诺书。
8. 演示结束回到主线:
   ```bash
   git checkout main
   ```

## 收尾钩子

今天这套东西的核心思想只有一句话:大模型只需要知道"这里有一个值",不需要知道"这个值是什么"。
入站脱敏、工具层还原、出站回填,三道闸门围出一个结论:客户的真实号码从头到尾没有离开过我们自己的进程边界。
长期记忆那一关也没漏:上一集做的记忆提取,凡结果里带占位符的条目直接丢弃,PII 连跨会话存储的门都摸不到。
数据安全了,但故事没完。
系统前阵子在线上出过一次路由错误:客户要查明细,请求被路由去了账户专员,答案文不对题。
老板来问两句话:"哪一步错了?为什么错?"
你打开终端,只有一堆滚动日志,哪条日志属于那次请求、大模型当时看到了什么、工具返回了什么,全靠你脑补和猜。
更尴尬的是,这次请求里还带着刚脱敏的占位符,日志里满屏的 [PHONE_1],你连"当时客户到底提供了哪个号码"都拼不回去。
猜,是没法向老板和合规交代的。
下一集我们给系统装上 Langfuse:每一次请求一条完整 trace,每一环的输入输出、耗时、成本全部留痕。
到时候我们再回到 PII 这个主题,你会在 trace 里亲眼看到一件事:大模型的输入里,真的只有 [PHONE_1]。
今天我说的话,下一集全部变成可以截图、可以回放、可以摆到老板面前的证据。
我们下集见。
