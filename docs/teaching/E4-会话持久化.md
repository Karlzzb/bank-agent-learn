# E4 会话持久化

> 对应 git tag:`e4`(与 e5/e6 同 commit;记忆与 PII 主题留给对应集,本集只讲持久化与共享状态)
> 本集痛点:电话一断,客户要把身份、诉求、办到哪一步从头再说一遍。
> 上一集:E3 认证与授权 | 下一集:E5 记忆管理

## 开场话术

你打银行客服电话,报了身份证号,验证了手机号,说了诉求,客服刚帮你查到一半——电话断了。
你重拨,换了一个客服,开口第一句:"您好,请问有什么可以帮您?"
于是你把身份、诉求、刚才办到哪一步,从头到尾再说一遍。
这种体验每个人都遇过,每个人都恼火。

上一集我们的 AI 客服学会了"只认 token 不认嘴",安全关算是过了。
但今天它还是那个接电话就失忆的客服:进程一重启、连接一断,前面聊的全部作废。
demo 里没人会重启进程,可生产环境里部署、扩容、崩溃、发布,每一天都在重启。
一个不能续聊的客服系统,上线第一天就会被投诉淹没。
所以别把"会话持久化"当成锦上添花的功能项,它是任何对话系统从玩具跨进生产的那道门槛。

还有一个单 Agent 时代不存在的麻烦。
我们把系统拆成了调度员加三个领域专员,对话状态不再住在一个地方:谁都能往共享状态里写东西的话,你改我的、我盖你的,聊三轮状态就是一锅粥。
单 Agent 系统里状态一致性是"别出 bug"的问题;多智能体系统里它是"先立宪法"的问题——谁有资格写哪个字段,必须白纸黑字定下来,不是靠约定俗成的默契。

可能有观众会问:为什么不用 Redis、不用数据库集群,就一个 SQLite 文件?
教学阶段我们先守住最核心的东西:状态必须持久化、必须能按会话号精确取回、进程退出必须退得干净。
存储选型是部署期的事,契约是设计期的事;契约立对了,底层从 SQLite 换成 PostgreSQL 只是改配置。

今天我们做两件事:一是让会话落盘,断线、重启都能凭一个会话号原样接上;二是给共享状态立规矩,每个键谁写、怎么合并,全部钉死,还要用测试盯着。

## 概念要点

- **SQLite checkpointer:会话状态的落盘点**:每轮对话结束,整份图状态写进本地 SQLite 文件 `checkpoints.sqlite3`,路径由配置 `CHECKPOINT_DB_PATH` 指定。
  装配与回收在 `src/bank_agent/memory/checkpointing.py`,用的是 LangGraph 的 `AsyncSqliteSaver`。
  一句话讲法:"每聊完一轮,给整份对话状态拍张快照存进数据库;下次凭会话号把快照调出来,接着往下走。"
- **thread_id 就是会话号**:每个会话一个 ID,调图时经 config 传入;进程重启后凭同一个 thread_id 续聊,上下文一条不丢。
  拼装处在 `src/bank_agent/chat.py` 的 `invoke_chat`,这是所有入口(CLI、HTTP)共用的唯一契约。
- **共享状态的写者与 reducer 规则**:定义在 `src/bank_agent/state.py`,四条铁律——`messages` 是共享键,所有节点只追加,合并规则是 `add_messages`;`route` 和 `rationale` 的唯一写者是 Coordinator,每次路由整体覆盖;`pii_map` 的唯一写者是调图入口,图内节点一律不写;子图私有键(如 `tool_steps`)定义在子图自己的 schema 里,不进入父图状态。
- **防循环是两层兜底**:Coordinator 与子 Agent 之间一跳往返由图结构保证,根本没有回边;万一失控,调图处的 `recursion_limit`(25 步)兜底,超限返回降级话术而不是死循环,见 `src/bank_agent/chat.py`。
- **进程退出要退得干净**:checkpointer 持有的 SQLite 连接是非守护线程,不主动关闭进程退不出;FastAPI 的 lifespan 在退出时释放组合根持有的连接,见 `src/bank_agent/api.py`。
  一句话讲法:"挂了资源不撒手,进程就会变成杀不掉的僵尸;谁申请谁归还,组合根统一收口。"
- **两个入口同一套续聊契约**:CLI 退出时打印本次会话 ID,重开 `python -m bank_agent.cli <id>` 接着聊(`src/bank_agent/cli.py`);HTTP 路径 `POST /chat` 请求体可带 `thread_id`,响应原样返回(`src/bank_agent/api.py`)。

## 演示步骤

1. 检出本集 tag 并起栈:
   ```bash
   git checkout e4
   make run    # 种子数据 + 3 个 MCP Server + API
   ```
   预期:种子库就绪,MCP Server 与 API 全部启动,终端不退出、保持前台运行。

2. 另开一个终端,起 CLI 聊上两三句:
   ```bash
   make cli
   ```
   输入"帮我查一下余额",再输入"把地址改成上海市浦东新区世纪大道 100 号"。
   预期:两条都正常办理;注意第二轮它知道"你"是谁、接着上一轮的语境,不需要重新自我介绍。

3. 输入 `quit` 退出 CLI。
   预期:退出前打印一行"本次会话 ID:<一串十六进制>(下次可用 python -m bank_agent.cli <id> 续聊)"。
   (镜头:把这串 ID 放大给观众看——"这就是续聊的钥匙")

4. 模拟"进程重启后的重拨":拿上一步的会话 ID 重开 CLI,直接追问刚才的事:
   ```bash
   python -m bank_agent.cli <上一步打印的会话ID>
   ```
   进入后输入"我刚才把地址改到哪了?"
   预期:启动时打印"继续会话:<id>";追问能正确接上,答出"上海市浦东新区世纪大道 100 号"。
   (讲解:这是一个全新进程、全新的图对象,它之所以能接上,是因为状态不在内存里,而在磁盘上)
   (镜头:语气放慢——"刚才那台'客服'已经被杀掉了,现在接你电话的是新上岗的一台,但它记得你聊过的每一个字")

5. 给观众看 checkpoint 真实落盘(只读查询,不动数据):
   ```bash
   sqlite3 checkpoints.sqlite3 ".tables"
   ```
   预期:列出 checkpoints 等表。
   (镜头:强调"不是玄学,就是一个 SQLite 文件;银行生产环境换成 PostgreSQL 版本即可,契约不变")

6. 换 HTTP 路径演示同一契约。
   先取 token,再连发两问,第二问带上第一问返回的 thread_id:
   ```bash
   TOKEN=$(python -m bank_agent.auth.idp C001)
   curl -s -X POST http://127.0.0.1:8000/chat \
     -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
     -d '{"message":"帮我查一下余额"}'
   ```
   预期:响应 JSON 里含 `thread_id`、`reply`、`route` 三个字段。
   ```bash
   curl -s -X POST http://127.0.0.1:8000/chat \
     -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
     -d '{"message":"顺便把地址改了,还是世纪大道 100 号","thread_id":"<上一步返回的thread_id>"}'
   ```
   预期:响应里的 `thread_id` 与传入的一致,业务正常办理。
   (讲解:CLI 和 HTTP 走的是同一个 `invoke_chat`,续聊契约只有一份,不存在"两个入口两种行为")

7. 打开 `src/bank_agent/state.py` 现场走读四条写者规则,再打开 `tests/test_memory.py`,指着 `test_resume_after_process_restart` 与 `test_shared_state_writer_rules_and_private_key_isolation` 两个测试:
   预期:前者用两个组合根模拟"进程重启"断言续聊后上下文完整;后者断言共享键恰好是约定的四个、`messages` 只追加、`route` 被最新路由覆盖、子图私有键 `tool_steps` 不泄漏到父图。
   (讲解:规则不是写在注释里求人遵守,是有确定性测试盯着的,全部本地运行、零 API 消耗)
   (镜头:逐行念出断言——"共享键恰好四个,多一个少一个都算事故;这不是风格洁癖,这是多智能体系统的交通法规")

8. 回归测试并切回主线:
   ```bash
   make test
   git checkout main
   ```
   预期:全部测试通过。
   (讲解:注意我们全程没为"持久化"写一句新提示词——这是架构能力,不是 prompt 技巧;模型一个字没变,系统行为天差地别)

## 收尾钩子

今天之后,我们的客服系统不再失忆:会话落在 SQLite 里,进程随便重启,凭一个会话号原样接上;共享状态的每个键谁写、怎么合并,白纸黑字还有测试盯着。
"断线重拨从头再说"这个工业级痛点,算是正面解决了。
回头看整条叙事链:E1 翻车、E2 拆分、E3 管住凭证、E4 管住状态——系统已经是一个"能上班"的客服了。

但新的麻烦已经藏在今天的演示里了。
聊得越久,`messages` 只追加不删除,上下文越滚越大——token 成本一路上涨,模型还会"前说后忘",最早聊的细节被挤出注意力。
更别扭的是跨会话:用户这次说了"我常用 A002 账户",明天新开会话,系统又一脸茫然。
续聊解决的是"一个会话不断",解决不了"会话越来越长"和"跨会话记不住人"。
这两个问题靠堆上下文都解决不了,需要的是一套真正的记忆机制。
